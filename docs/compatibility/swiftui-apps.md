# Third-party SwiftUI apps on AppKitCross

Whole apps, as opposed to the libraries in [swiftui-libraries.md](swiftui-libraries.md):
a real open-source SwiftUI macOS app vendored under `Examples/` unmodified and built against
the port, as the end-to-end measure of where the port stands. Each entry lists what the app
uses, what broke, what was fixed in the port for it and what is left.

## Daily To Do (`Examples/DailyTodo`, 2026-11-12)

[Noreen21/daily-todo](https://github.com/Noreen21/daily-todo), MIT, 1,075 lines of Swift,
vendored at commit `213775aa` (2026-11-06). Chosen because it is a plain SwiftPM package with
no third-party dependencies, pure SwiftUI (no SwiftData, Core Data, SpriteKit or WebKit), and
exercises the everyday surface: a `NavigationStack` with a toolbar, a date field, a text field,
a list of checkbox rows, an empty-state view, a settings sheet with a grouped form, pickers,
read-only rows, `environmentObject`, JSON file persistence, a timer, plus two Apple frameworks
the port lacks (`UserNotifications`, `ServiceManagement`). Alternatives looked at and why not:
Infinity Notes (SwiftData models and `@Query`, which need the macro and a persistence layer
the port has no counterpart for), TomatoBar (a menu-bar-only app over Carbon hot keys and
`LaunchAtLogin`), Pomosh (Xcode project with HotKey, IOKit and WebKit), CmdMD (31,000 lines).

Status: builds on the macOS host build against the port's SwiftUI and the real
UserNotifications/ServiceManagement; builds on Windows and Linux against the shims (CI); the
app's own self-checks (`DailyTodoChecks`) build on every CI job and run on the macOS and Linux
jobs (on Windows the PC runs them: they assert POSIX file permissions, which corelibs may
report differently there). Its two screens, rebuilt from
the same views in `Tests/AppKitTests/SwiftUIRealAppTests.swift`, host and work on the headless
backend (the empty state comes and goes with the rows, the toolbar button opens the settings
sheet, the grouped form shows the time picker, the pop-up and the read-only rows, the toggle
drives the model and the read-only row follows, Done dismisses). The Windows PC run is
recorded in the pull request.

### The Windows run (2026-11-13)

The PC ran the checklist on the Win32 backend (built at 8c0a271). Passed as written: the
menus (Ctrl+A/C/V, Select All, Cut, item enabling), quitting and relaunching with the saved
tasks, the JSON file under `%LOCALAPPDATA%\DailyTodo\daily-todo.json` with no save error,
deferring (dueDate and deferredCount written correctly), and `DailyTodoChecks` ("All
DailyTodo checks passed."). What it found, and what each turned out to be:

| PC finding | Root cause | Owner in `Sources/` | Status |
| --- | --- | --- | --- |
| Window title and app menu read "DailyTodo.exe", not "Daily To Do" | `_AppRunner` named the app after the executable file, extension included, and `.navigationTitle` only reached the `NavigationStack`, never the window (macOS titles a WindowGroup's window with its content's navigation title). | `SwiftUI/App.swift`, `SwiftUI/Navigation.swift` | Fixed: the name is `CFBundleName` or the executable's stem; the navigation title titles the hosting window (test). |
| Not resizable (no `WS_THICKFRAME`) although the app sets `windowResizability(.contentSize)` with a frame minimum | `.contentSize` removed `.resizable` and pinned the window to its opening size; on macOS it is the content's size *range* (minimum to maximum), fixed only when the two meet. | `SwiftUI/App.swift` | Fixed: the window's min and max come from the content's `sizeThatFits(0)` and `sizeThatFits(∞)`; it opens at the content's ideal size; no resize frame only for content of one size (tests: this app's screen resizes from 560×420 up, a 240×120 view stays fixed). |
| A 35 px band between the toolbar and the Day row at launch; the "N pending" footer vanishes once there are rows | `ScrollView` (what a `List` is built on) answered a stack's flexibility probe with its content height, so the `VStack` never gave the list the leftover height: an empty list left the column short and centred (the band), a full one pushed the footer out. | `SwiftUI/Views.swift` (`_ScrollPrimitive`) | Fixed: along its scroll axes a scroll view takes what it is offered and reports infinite flexibility, as on macOS (test: the Day row at the top, the footer at the bottom, with and without rows). |
| Text typed as one fast `SendInput` burst comes out as the last character repeated ("tttttttttttttttt"); key by key works | Injected Unicode arrives as `VK_PACKET` key-downs whose character is in the message's scan code; `ToUnicode(VK_PACKET)` returns the thread's *latest* injected character, so every key-down in a queued burst read the last one. `TranslateMessage`'s `WM_CHAR` is the message's own. | `AppKit/Platform/Win32/Win32Window.swift` | Fixed (not verifiable off Windows): a `VK_PACKET` key-down takes the translated `WM_CHAR` units, as a key `ToUnicode` cannot translate already did. |
| The field keeps showing the added text until focus leaves | `_TextFieldPrimitive` skipped a binding change while the field editor was open. | `SwiftUI/Views.swift`, `AppKit/Core/NSTextField.swift` | Fixed: the binding updates the field editor too (test: Add clears the focused field). |
| Ticked rows are dimmed but not struck through | Nothing drew `.strikethroughStyle`: CoreText draws underlines from the line attributes, and AppKit's layout manager draws strikethroughs itself, which the port's never did (on macOS either). | `AppKit/Core/NSLayoutManager.swift` | Fixed: `drawGlyphs` strikes every `.strikethroughStyle` run through its fragments in the text (or strikethrough) colour. Not pixel-tested. |
| The date field takes focus but ignores Up/Down and digits | `_DatePickerPrimitive` set the picker's `locale` on every body update, and the cell's `locale` setter resets the selected field, so the field was deselected before or after each key. | `SwiftUI/Views.swift`, `AppKit/Core/NSDatePickerCell.swift` | Fixed: the locale (and elements) are set only when they change (test: Up steps the day twice and the field stays selected). |
| The toolbar Settings item does nothing (no sheet) | A toolbar band drags the window on Windows (`WM_NCHITTEST`), and the window's hit test let a press on the custom button's label through as caption: the press became a drag before any view saw it. | `AppKit/Core/NSWindow.swift` (`platformWindowHitTest`), `SwiftUI/Runtime.swift` (`_ContainerView`) | Fixed: a container that handles presses is a control for the window, and the hit view's ancestors are consulted, so a label inside a custom button is the button's (test: the hit region over the button is client). No "Settings…" menu item is correct: the app has no `Settings` scene, and macOS shows none either. |
| The close box only shows its tooltip | `Win32Window` captured `WM_NCLBUTTONDOWN` on `HTCLOSE` for the package-drawn caption buttons of custom-frame windows, with the system frame too, so `DefWindowProc` never tracked the real button. | `AppKit/Platform/Win32/Win32Window.swift` | Fixed (not verifiable off Windows): only a custom frame takes caption-button presses. |
| File > Close leaves the process running with no window and no way back | AppKit's rule: an app keeps running after its last window closes (the Dock reopens it). Windows and Linux have no Dock, so a SwiftUI app without a status item is unreachable. | `SwiftUI/App.swift` | Fixed as a policy: off macOS a SwiftUI app terminates when its last scene window closes, unless it has a status item or its delegate answers `applicationShouldTerminateAfterLastWindowClosed` itself. The app's own "keep running after closing the window, reopen at the workday start" needs a tray icon on Windows: a follow-up for the app, not the port. |
| The main thread spins a full core while idle | Gone with the fixes above (the re-check measured 0.02 s CPU over 5 s). The likeliest cause was the date picker: every SwiftUI body update set the cell's locale, whose setter invalidated the control, which scheduled a frame, whose body update set the locale again. | `SwiftUI/Views.swift` (`_DatePickerPrimitive`) | Fixed by the date picker change (the scroll view sizing change is the other candidate). |
