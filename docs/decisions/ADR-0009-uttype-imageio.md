# ADR-0009: UniformTypeIdentifiers and ImageIO on Windows and Linux

Date: 2026-10-28. Status: accepted.

## Context

Mac apps and SwiftUI reach for two small frameworks next to AppKit without thinking
about them: `UTType` (save panels, drag and drop, document types, `NSPasteboard`) and
ImageIO's `CGImageSource` / `CGImageDestination` (anything that reads or writes image
files below `NSImage`). Neither exists on Windows or Linux, so source written against
them did not compile here.

## Decision

Two leaf modules in the package, declared only on Windows and Linux as `CoreGraphics` and
`CoreText` are (ADR-0007): on macOS the tests run against Apple's implementation, which
is the specification, and the same tests run against ours in the Linux container.

- `Sources/UniformTypeIdentifiers`: `UTType` and `UTTagClass` with Apple's API, pure
  Swift. The type database is `UTCoreTypesTable.swift`, generated by
  `tools/uttypes/dump-core-types.swift` from the macOS SDK: every `UTType` constant's
  identifier, direct supertypes, filename extensions, MIME types, description, reference
  URL and version, plus the supertypes those reach. There is no LaunchServices on these
  platforms, so `UTType(exportedAs:)` / `UTType(importedAs:)` declare the type in a
  process-wide registry with the given parent (Apple reads the bundle's Info.plist and
  ignores the parameter for declared types), and later lookups find it. Unknown tags
  produce dynamic types with Apple's exact `dyn.a…` encoding, so identifiers match across
  platforms and decode back to their tag. `Codable` writes the identifier string and
  also reads Apple's keyed form.
- `Sources/ImageIO`: `CGImageSource` and `CGImageDestination` as opaque classes with
  Apple's C function names, over the package's codecs: WIC through the `CD2D` shim on
  Windows, Cairo's PNG stream reader and writer on Linux. ImageIO does not depend on
  AppKit; it calls the C modules directly. The CF container types in the signatures are
  CoreText's typealiases (`CFString`, `CFData`, `CFMutableData`, `CFDictionary`,
  `CFArray`, `CFURL`), re-exported, so a file importing both modules sees one set of
  names. `CopyTypeIdentifiers` reports what the platform codec really handles: PNG on
  Linux; PNG, JPEG, GIF, TIFF, BMP and ICO sources and PNG/JPEG destinations on Windows.
  Properties come from the PNG header (`PixelWidth`, `PixelHeight`, `Depth`, `HasAlpha`,
  `ColorModel`, `DPIWidth`/`DPIHeight` from `pHYs`, the `{PNG}` dictionary) without
  decoding; other containers decode to report them.

AppKit keeps using its platform image backends, so `NSImage(data:)` and
`NSBitmapImageRep` behave as before; the modules are there for application code and for
SwiftUI.

## Consequences

- Behaviour that is not modelled is honest: `CGImageDestinationCopyImageSource` and the
  metadata API (`CGImageMetadata`) are absent, EXIF orientation is not read (so
  `kCGImagePropertyOrientation` is never reported), and encoding a pixel layout the
  codecs cannot take traps through the module's `unimplemented()`.
- Apple's `UTTypeReference` bridging class and `URLResourceValues.contentType` are out of
  scope; the `URL.appendingPathComponent(_:conformingTo:)` family is included.
- Regenerate the table when the SDK changes: it is generated, not edited.
