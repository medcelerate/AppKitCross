# Third-party SwiftUI apps on AppKitCross

Whole apps, as opposed to the libraries in [swiftui-libraries.md](swiftui-libraries.md):
a real open-source SwiftUI macOS app vendored under `Examples/` unmodified and built against
the port, as the end-to-end measure of where the port stands. Each entry lists what the app
uses, what broke, what was fixed in the port for it and what is left.

## Daily To Do (`Examples/DailyTodo`, 2026-11-12)

[Noreen21/daily-todo](https://github.com/Noreen21/daily-todo), MIT, 1,075 lines of Swift,
vendored at commit `213775aa` (2026-11-06). Chosen because it is a plain SwiftPM package with
no third-party dependencies, pure SwiftUI (no SwiftData, Core Data, SpriteKit or WebKit), and
exercises the everyday surface: a `NavigationStack` with a toolbar, a date field, a text field,
a list of checkbox rows, an empty-state view, a settings sheet with a grouped form, pickers,
read-only rows, `environmentObject`, JSON file persistence, a timer, plus two Apple frameworks
the port lacks (`UserNotifications`, `ServiceManagement`). Alternatives looked at and why not:
Infinity Notes (SwiftData models and `@Query`, which need the macro and a persistence layer
the port has no counterpart for), TomatoBar (a menu-bar-only app over Carbon hot keys and
`LaunchAtLogin`), Pomosh (Xcode project with HotKey, IOKit and WebKit), CmdMD (31,000 lines).

Status: builds on the macOS host build against the port's SwiftUI and the real
UserNotifications/ServiceManagement; builds on Windows and Linux against the shims (CI); the
app's own self-checks (`DailyTodoChecks`) build on every CI job and run on the macOS and Linux
jobs (on Windows the PC runs them: they assert POSIX file permissions, which corelibs may
report differently there). Its two screens, rebuilt from
the same views in `Tests/AppKitTests/SwiftUIRealAppTests.swift`, host and work on the headless
backend (the empty state comes and goes with the rows, the toolbar button opens the settings
sheet, the grouped form shows the time picker, the pop-up and the read-only rows, the toggle
drives the model and the read-only row follows, Done dismisses). The Windows PC run is
recorded in the pull request.

## MD Vault (`Examples/MDVault`, 2026-11-16)

[AadeshTaneja/md-vault](https://github.com/AadeshTaneja/md-vault), MIT, 1,773 lines of Swift
in `Sources/`, vendored at commit `eff8e40d` (2026-09-27). The second app and the first
document-based one. Chosen because it is a `DocumentGroup` over a `FileDocument` with an
`NSTextView` representable as its editor (undo, the find bar, a syntax highlighter on the text
storage), a Markdown viewer written in SwiftUI from its own parser (attributed text, `Grid`
tables, images, lists, code blocks), a toolbar picker, `Commands` driven by `@FocusedValue`,
`@AppStorage`, `UTType(importedAs:)` and an Info.plist with document types, with no
dependencies, no WebKit and a plain `swiftc` build. Looked at and why not: TextViewer
(andrewneuwirth/textviewer, MIT, 2,059 lines, a SwiftPM package with a `DocumentGroup`: mostly
a viewer, refuses Markdown, ships a QuickLook extension target, its editing is a mode of a
read-only view), Markra (dduan/Markra, MIT, 802 lines: The Composable Architecture,
SwiftUI-Introspect and swift-markdown dependencies through an XcodeGen project, last touched
2022), and the Markdown editors with a preview (Glim, MapleDown, mdeditor, Margin, MacMD:
`WKWebView` previews), plus mark-mac (three third-party packages) and SwiftUIMarkdownEditor
(139 lines, a `WKWebView` preview). Neither MD Vault nor the alternatives without WebKit have
a sidebar or a `Settings` scene; MD Vault's settings are its View-menu commands.

Status: builds on the macOS host build and in the Linux container; the CI jobs build it on
Windows and Linux. Its document flow, rebuilt from the same shapes in
`Tests/AppKitTests/SwiftUIDocumentAppTests.swift`, runs on the headless backend: a new
untitled document in a window of the scene's default size, typing through the `NSTextView`
representable into the document binding, the edited mark, Save to a file, close, reopen with
the contents, revert, Undo back to an unedited document and Redo, the File menu a
`DocumentGroup` gets, a View-menu command disabled with no document and acting on the key
window's `focusedSceneValue` binding with one, and the viewer's shapes (attributed runs with
`NSFont` fonts, links, strikethrough and code backgrounds; a `Grid` table; a horizontally
scrolling code block; `.bar`; `textSelection`) laid out and drawn. The vendored executable
was not launched on the Mac (the session's sandbox refuses to run a downloaded program); the
Windows run is the PC checklist in the pull request. `APPKITWIN_TEXTKIT` does not exist yet
(the TextKit 2 session is in flight): the editor runs on the default (TextKit 1) engine.

This pull request is based on PR 79 (core depth round 2), which the app needs: there an
`NSTextViewDelegate` that does not implement `textView(_:shouldChangeTextIn:replacementString:)`
lets the change through (the generated default returned `false`, so no typing reached the
editor at all), and `NSTextView` registers undo with the window's undo manager (the
document's), which the document's edited state follows.
